# Architect Engine + Deepesh Mobile Studio

This repository currently contains two related but independently runnable codebases:

1. **Architect Engine** — Flutter Android app for architectural projects, CAD drafting, calculators, and project storage.
2. **Deepesh Mobile Studio** — Python/Termux video-production toolkit with narration, asset generation, audio mixing, and rendering workflows.

## Repository map

| Path | Purpose |
|---|---|
| `lib/` | Architect Engine Flutter application |
| `pubspec.yaml` | Flutter dependencies and SDK constraints |
| `architect_engine_renderer.py` | Concept-plan JSON to SVG renderer |
| `tools/architect_engine_feasibility_check.py` | Geometry screening report (not building-code approval) |
| `Deepsh mobile studio/` | Mobile-first Python video-production studio |
| `Deepsh mobile studio/core/` | Rendering, asset, synchronization, audio, and voice modules |
| `Deepsh mobile studio/tests/` | Offline Python unit tests |
| `.github/workflows/` | Android build and Cartesia offline test workflows |

## Architect Engine: build

Requirements: Flutter stable with Dart 3.x and Java 17.

```bash
flutter pub get
flutter analyze
flutter test
flutter build apk --release
```

The Android CI workflow provisions the Android project files when they are not checked in, then builds a release APK.

**Current implementation boundary:** the CAD editor contains DXF and PDF drawing export. The separate Export Center screen is still a presentation/entry-point placeholder and must not be treated as a completed multi-format export pipeline. PNG/SVG/BOQ export availability must be verified in the relevant feature before promising it.

## Deepesh Mobile Studio: Android / Termux setup

Requirements include Python 3, FFmpeg/FFprobe, and the packages installed by the setup script.

```bash
cd "Deepsh mobile studio"
sh setup_mobile.sh
python3 studio.py selftest --quick
```

For a new production project:

```bash
python3 studio.py new ~/videos/my_video
cd ~/videos/my_video
```

Follow the studio's `README.md`, `MOBILE_GUIDE.md`, and `ENGINE_V2.md` for the full production workflow.

## Cartesia voice engine

The Cartesia voice-direction planner, pronunciation normalizer, audio analyzers, narration audits, and retake review tools are designed to run locally where possible.

- Set `CARTESIA_API_KEY` only in the local environment; never commit credentials.
- Direction planning, pronunciation previews, audio analysis, and offline tests do not require Cartesia credits.
- Synthesis and retake execution do consume provider credits.
- Run `python -m unittest discover -s tests -p "test_*.py" -v` from `Deepsh mobile studio/` for the offline test suite.
- Signal metrics and heuristic audits are not proof of naturalness, correct pronunciation, or intelligibility. Human listening remains required.

## Important limitations

- Architectural geometry/feasibility scripts are screening and visualization tools, not certified architectural, structural, municipal, or code-compliance approval.
- Do not treat generated plans as construction-ready without review by a qualified local professional and verification against the applicable regulations.
- Third-party fonts, music, sound effects, and bundled media require independent licence/provenance checks before commercial publication.
- Google Flow bridge workflows require the user's own browser session and local bridge service.

## Development policy

- Keep provider/API calls out of CI.
- Keep generated bytecode, caches, build output, and local secrets out of version control.
- Validate changes on the feature branch before merging to `main`.
